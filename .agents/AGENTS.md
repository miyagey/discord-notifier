## 2. 設計原則とコード生成制約（プロンプトルール）

### 2.1 レイヤー分離とオーケストレーションの徹底
- `spreadsheet/定期通知バッチ.js` などのオーケストレーション層では、**「データ取得」「メッセージ整形」「送信」のフロー制御のみ** を記述する。
- バッチ処理関数内に、直接 Discord メッセージの Markdown を長文連結したり、スプレッドシートの生データを加工するロジックを混在させてはならない。

### 2.2 定期通知バッチ (`spreadsheet/定期通知バッチ.js`) のコーディング規約
AI エージェントがバッチ処理スクリプトを作成・編集する場合は、以下の設計ルールを**厳格に遵守**すること。

1. **オーケストレーション層の単一責任原則**:
   - `定期通知バッチ.js` 内のメイン関数は、データの取得・処理呼出・エラーハンドリング・ログ出力の**高レベルな司令塔（オーケストレーション）のみ**を担当すること。
   - メイン関数内で以下の処理を行ってはならない：
     - メッセージ（Discord Embed）の組み立てや文字列整形
     - シートの二次元配列に対するフィルタリングや直接ループ処理
     - `new Date()` や日付フォーマット処理（`yyyy-MM-dd` 変換等）の呼び出し
2. **ガード節（早期 return / アーリーリターン）の禁止と一本道フローの維持**:
   - メイン関数内で `if (items.length === 0) return;` のようなガード節（途中の早期離脱）を記述してはならない。
   - 取得データが 0 件の場合の「対象なし」ログ出力や通知送信スキップ処理は、**呼び出し先のサービス層（`DiscordService` や `CalendarService`）の内部で実装**すること。
   - メイン関数は必ず `try...catch` を通して、関数末尾の完了ログ（`Logger.log("=== ...が正常終了しました ===")`) まで到達する一本道の構造に保つこと。
3. **引数の暗黙的カプセル化と DTO パターン**:
   - バッチ処理で実行時の「現在日付」が必要な場合、メイン関数で生成してサービス層に引数として渡さないこと。日付生成はサービス層内部で完結させること（引数なしで呼び出せる設計）。
   - サービス層間で受け渡すデータは、配列インデックスに依存した生の配列ではなく、名前付きプロパティを持つオブジェクト（DTO）の配列として扱うこと。

### 2.3 データアクセス層の完全カプセル化
- スプレッドシートの列インデックス（`MASTER_COL`, `APPLY_COL`）は `spreadsheet/スプレッドシート操作.js` 内に閉じた定数とする。外部ファイル（`設定値.js` やバッチファイル）へ露出・定義してはならない。
- 呼び出し側では、配列の生インデックス（`row[0]` や `row[1]` 等）を直接参照せず、必ず `SheetService` から返却される名前付きプロパティを持つオブジェクト（DTO）を扱うこと。

### 2.4 DTO (Data Transfer Object) / Parameter Object パターン
- 3つ以上の引数や省略可能オプションを持つ関数・メソッドは、単一のオブジェクト引数形式（例: `{ title, startDate, endDate, location, summary }`）で受け取るように設計し、詳細な JSDoc コメントを付与すること。

### 2.5 マジックナンバー・直インデックスの禁止
- シートの列番号や設定値は直接数値で記述せず、内部定数やオブジェクト定数を経由すること。

### 2.6 関数の配置ルール（トップダウン記述）
- エントリーポイントとなる**メイン処理関数をファイルの最上部に配置**する。
- 呼び出されるヘルパー関数やデータ抽出関数は下部に配置し、ファイルの可読性と流れを明確に保つ。

### 2.7 ドキュメント内の図・ダイアグラム表現（Mermaid 記法の必須 & 描き分け基準）
- `docs/` 配下や README 等のドキュメント内でアーキテクチャ図、データフロー図、処理シーケンスなどの図解を用いる場合は、画像や ASCII アートではなく**必ず Mermaid 記法（` ```mermaid `）を使用すること**。
- パースエラー防止のため、ノードや矢印のラベル内に括弧 `()` などの記号を含める場合は、必ずダブルクォートでエスケープすること（例: `-->|"データ操作 (SheetService)"|`）。
- **Mermaid 描き分け基準**:
  - **交差・折れ曲がりの最小化**: データ・モジュール層を 3 階層（入力/UI ➔ バックエンド/処理 ➔ 外部連携/DB）に明確化し、矢印ラベルに数字（1., 2.等）を付けずデータ通信の内容のみを記述する。
  - **`docs/SYSTEM_SPEC.md` 用（機能・データフロー図）**: 内部コード名（`SheetService` 等）には踏み込まず、ユーザー操作・データストア（シート）・外部通知（Discord/カレンダー）の機能的繋がりを描画する。
  - **`docs/ARCHITECTURE.md` 用（モジュール・レイヤー構造図）**: `spreadsheet/` 配下のファイル構造（`Webアプリ.js`, `定期通知バッチ.js`, `SheetService`, `DiscordService`, `CalendarService`）に対応する層構造と依存関係（呼び出し方向）を明示する。

### 2.8 テスト適用範囲の制限
- オーケストレーション層（`定期通知バッチ.js` のメイン関数等）に対する単体テストコードは作成しない（モック肥大化防止）。
- 単体テスト（Vitest）は `共通関数.js` や `Discord操作.js`（Embedフォーマッター）、`SheetService` の純粋データ整形ロジックに集中して作成すること。

### 2.9 ドキュメント自動更新手順
- コード変更・リファクタリングを実施した場合は、必ず対になる `docs/ARCHITECTURE.md` または `docs/SYSTEM_SPEC.md` の記述・Mermaid図を同時に更新すること。

### 2.10 Discord 連携の棲み分け規約（Webhook vs Bot REST API）
- **全体ブロードキャスト・定期通知バッチ**: 原則として **Discord Webhook** を使用する（レートリミット独立・障害影響局所化・軽量性の維持）。
- **動的リソース作成・個別チャンネル管理・ライフサイクル操作**: 必ず **Bot REST API (`DiscordService.fetchDiscordApi`)** を使用する。

### 2.11 GAS × Discord Bot REST API のプロキシ & User-Agent 規約（Cloudflare WAF 40333 対策）
- **GAS の仕様制約と WAF ブロック**: GAS (`UrlFetchApp`) は `User-Agent` が `Google-Apps-Script` に強制固定されるため、Discord の Cloudflare WAF により Bot API リクエストが `40333: internal network error` で遮断される。
- **プロキシ経由の必須化と UA 上書き**: Bot REST API 呼び出しは必ず `PROXY_BASE_URL`（Cloudflare Workers 等）を経由させ、プロキシ側で `User-Agent` を Discord Bot 仕様（`DiscordBot (...)`）に上書きして転送する構成を前提とすること。
- **クライアントの統一**: Bot API 呼び出し時に直接 `UrlFetchApp` を叩かず、必ず認証・プロキシ置換・JSON パース・エラーハンドリングが集約された `DiscordService.fetchDiscordApi` を経由すること。

### 2.12 動的リソース生成時のサニタイズおよび外部 ID 永続化ルール
- **チャンネル名サニタイズ**: Discord チャンネル作成時は、HTTP 400（不正文字・文字数超過）を防止するため、必ず `DiscordService.sanitizeChannelName` によるサニタイズ（小文字化・記号除去・ハイフン区切り・99文字制限）を通すこと。
- **外部 ID の即時永続化**: カレンダー予定（`calendarEventId`）や Discord チャンネル（`discordChannelId`）等の外部リソースを動的作成した場合は、生成成功直後に必ずスプレッドシートの該当レコード（専用列）へ書き戻し（永続化）を行うこと。

### 2.13 サービス層および共通関数の設計規約
- **共通関数の配置基準**:
  - 特定の外部API（Discord, Calendar, Spreadsheet）に依存しない、純粋なデータ変換・フォーマット処理（日付のフォーマット、タイトルの文字列結合など）は必ず `共通関数.js` に配置すること。
  - `DiscordService` や `CalendarService` などの外部サービス用モジュール内に、汎用的な文字列整形関数を持たせてはならない。
- **イベントDTO受け渡しの原則**:
  - オーケストレーション層（`Webアプリ.js`, `定期通知バッチ.js`）でタイトル文字列や日付範囲文字列（`dateStr`）などの表示用データを事前生成してはならない。
  - サービス層（`CalendarService`, `DiscordService`）は、基本情報を持つイベントオブジェクト（DTO: `{ eventId, brand, eventName, startDate, endDate, venue, description }`）を引数として直接受け取り、必要な加工は各サービス内部で共通関数を用いて行うこと。

## 3. セキュリティ & クレデンシャル管理

### 3.1 機密情報の直接記述の禁止
- Discord Webhook URL、スプレッドシート ID、カレンダー ID などの機密情報は **ソースコード上に直接ハードコードしない**。
- **ローカル環境**: `config.local.js` で定義する。（`.gitignore` によりコミット対象外）
- **本番環境 (GAS)**: スクリプトのプロパティ (`PropertiesService.getScriptProperties()`) から取得する。

### 3.2 Git 管理対象外ファイル
- 以下は絶対に Git にコミットしないこと：
  - `config.local.js`
  - `.clasprc.json`
  - `node_modules/`

## 4. Git ブランチ & コミット規約

### 4.1 ブランチ運用 & タスク開始時のワークフロー
新しい作業・タスクを開始する際は、**必ず以下の最新化・クリーンアップ手順を踏んだ上で、目的に応じた専用の新規ブランチを作成して作業を行う。**

1. **`main` の最新化とマージ済みブランチの整理**:
   - `git checkout main`
   - `git pull origin main`
   - `git fetch --prune`
   - マージ済みローカルブランチの一括削除:  
     `git branch --merged main | grep -v '^\*' | grep -v 'main' | xargs git branch -d`
2. **専用作業ブランチの作成と切り替え**:
   - `main`: 安定した本番・最新コードブランチ
   - `feature/*`: 機能追加用の作業ブランチ
   - `fix/*`: バグ修正用の作業ブランチ
   - `refactor/*`: リファクタリング用の作業ブランチ
   - `docs/*`: ドキュメント作成・修正用の作業ブランチ

### 4.2 コミットメッセージの接頭辞
コミットメッセージは以下のプレフィックスを使用する：
- `feat:` 新機能追加
- `fix:` バグ修正
- `refactor:` リファクタリング（機能追加・バグ修正を含まない設計改善）
- `docs:` ドキュメント類（README, AGENTS.md等）の修正
- `style:` コードの意味に影響を与えない変更（フォーマット、空白等）

## 5. エージェントの作業範囲とデプロイ権限

### 5.1 エージェントが自律的に実施してよい操作
- 新タスク開始時の `main` 最新化・`git fetch --prune`・マージ済みブランチ削除
- 目的に応じた新規作業ブランチの作成と切り替え (`git checkout -b ...`)
- ローカルファイルの編集・作成・削除
- `git add` / `git commit`（コミットメッセージは規約に従う）
- `clasp pull`（GASからのコード取得）
- **作業ブランチ（`main` 以外）のリモートへの `git push`**
- **GitHub での Pull Request 作成（`gh pr create` 等）**

### 5.2 ユーザーが手動で実施する操作（エージェントは実行しない）
- `main` ブランチへの直接 push、および Pull Request のマージ操作
  - ※ PR が `main` へマージされると、GitHub Actions により本番 GAS へ自動デプロイされます。

> **理由**: 本番環境（`main` ブランチおよび本番 GAS）への直接反映は、人間が最終確認・判断した上で PR マージを行う。  
> 作業ブランチへの push および PR 作成まではエージェントが自律的に行い、ユーザーへ PR のレビュー・マージを案内する。
